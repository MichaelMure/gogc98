What am I looking at?

Reading this screen

Each row is one 8 KB page, Go's basic unit of memory management. A row's boxes are the objects living on that page, width proportional to their byte size relative to one page — not a fixed grid cell. A page of a thousand 8-byte objects looks like a dense strip of slivers; a single object bigger than one page fills every page it spans, edge to edge.

Row id: green means a real tracked page; dim means untracked (see "empty space" below). The right-aligned text is either the page's size class (colored blue–red by scale), +N meaning N more objects here exist but aren't individually tracked (there's a cap on how much detail gets sent per page, to bound message size), or i/n meaning this is page i of n belonging to one object bigger than a single page. Occasionally you'll see ?B instead — that page's own allocation event hasn't been seen yet (we first heard about it from one of its objects), so its size class genuinely isn't known yet, not just zero.

Box colors are just a hash of the object's Go type, so the same type always gets the same color within one view — the hue itself carries no meaning. Amber specifically means "untyped": an allocation like a raw []byte backing array that carries no type info at all. A green outline means just allocated; a fading red outline means just freed (it stays visible briefly so you can actually see frees happening, then disappears).

The strip above the page view is a minimap: one tick per tracked page across the entire heap, not just what's currently in view. Yellow = in the current view. Green, brightness scaled by recent activity = tracked but elsewhere.

Freeze pauses the heap snapshot itself (nothing changes, fade animations stop) while still letting you scroll around that frozen snapshot — useful for actually reading a moment instead of it changing under you.

Untracked page ids normally render as plain blank rows, one per id, even by the thousands — that's real information about how much of the heap's reserved address space isn't in use right now. Only a truly enormous run — large enough that it's almost certainly a jump to a completely different, distant region of address space rather than ordinary unused space — collapses into a single ⋯ N pages unused ⋯ row. See "what's actually in that empty space" below for why that distinction is about the best this tool can do.

What "the heap" actually is

It's tempting to picture the heap as one big pre-allocated block that Go carves objects out of. It's closer to the opposite: Go's heap is built from arenas, 64 MB chunks that get mapped in from the OS on demand as the heap grows. Go actively tries to keep arenas contiguous — each new one is requested right after the end of the last one — but that's a request to the OS, not a guarantee. If literally anything else in the process (a C library's own allocator if you're using cgo, a dynamically linked shared library, a direct mmap call, ASLR) has already claimed that exact address range, Go falls back to a completely different, far-away region instead. For a plain Go binary, that's rare — Go deliberately spreads its fallback addresses about 1 TB apart specifically to avoid this — but it's not architecturally impossible.

Within one contiguous run, page ids in this tool are literally adjacent bytes 8 KB apart: id 123 really is right after id 122 in virtual memory, because the id here is computed directly from real relative addresses, not just an arbitrary counter.

What's actually in that empty space? Almost always: address space Go has already reserved for the current arena but hasn't handed out to any span yet — not a hole, just unused. This tool can't directly tell that apart from a genuine jump to a different, non-contiguous arena (both just look like "nothing tracked here"), so it uses size as a proxy: only a gap in the millions of pages — far beyond what one contiguous arena run would plausibly leave unused, and approaching the ~1 TB spacing Go uses between its fallback addresses — collapses into a single ⋯ pages unused ⋯ row. Anything smaller, even thousands of pages, renders as ordinary blank rows, because that's still likely the mundane kind and is worth being able to actually see.

One more thing worth knowing: adjacency doesn't mean relatedness. Go's page allocator picks free page ranges via a best-fit-style search over its free list, not by simply appending after the last allocation. Two neighboring rows in this view can be totally unrelated spans — different types, different ages, allocated at completely different times — that just happen to have landed next to each other.

Pages, spans, and size classes

A span is one or more contiguous pages handed to the allocator to hold objects of exactly one size class. Go rounds every small allocation up to one of ~67 fixed size classes (8, 16, 24, 32, 48… up to 32768 bytes) instead of packing objects at their exact requested size. That's the whole reason every box in a row is the same size class — a page never mixes them — and it's a deliberate tradeoff: a little wasted space per object (the gap between a requested size and its rounded-up class) buys much simpler, faster bookkeeping and lets same-size objects share pages cleanly. Objects bigger than 32 KB skip size classes entirely and get a dedicated span sized to exactly cover them, rounded up to whole pages — that's the i/n case above.
